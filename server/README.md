# Аккаунты и синхронизация Lumo

Express обслуживает JSON API и сборку сайта. Локально PGlite сохраняет PostgreSQL-данные в `.data/lumo/`; размещённый сервер требует внешний PostgreSQL. Каталог базы, `.env` и журналы исключены из Git. Пакеты зафиксированы в lock-файле. Настройки этапа 8 — в [инструкции размещения](../docs/deployment.md).

## Запуск

Из корня проекта:

```powershell
pnpm install --frozen-lockfile
pnpm dev
```

Фронтенд: http://127.0.0.1:5173. API: http://127.0.0.1:3001. Vite перенаправляет `/api` на API, поэтому браузер видит один origin — сочетание протокола, адреса и порта. Если pnpm не доступен в PATH, после установки зависимостей работает `node scripts/dev.mjs`. Ctrl+C останавливает оба процесса. После изменения серверных исходников эту команду нужно перезапустить.

Для запуска только сервера: `pnpm dev:api` или `node server/index.js`. Не запускайте одновременно второй API на том же порту и с той же локальной базой. Для отдельного фронтенда есть `pnpm dev:web`.

`.env` необязателен для локального запуска. Если нужны настройки, скопируйте `.env.example` в `.env`. Сервер читает его при запуске. `APP_ORIGINS` — список разрешённых адресов сайта через запятую, без завершающего `/` и без `*`.

Для телефона в той же Wi-Fi сети фронтенд запускается с `pnpm exec vite --host 0.0.0.0`. Добавьте адрес вида `http://IP-КОМПЬЮТЕРА:5173` в `APP_ORIGINS` и перезапустите API. API может оставаться на `127.0.0.1`: запросы телефона к `/api` передаёт Vite. Локальный HTTP подходит для демонстрации с тестовыми данными; опубликованный вход требует HTTPS.

## Данные и вход

- Логин: 3–32 латинские буквы, цифры или `_`; регистр не различается.
- Пароль: 15–128 символов; разрешены пробелы и Unicode. Вставка и менеджеры паролей поддерживаются.
- Email и дата рождения не запрашиваются.
- Пароли хранятся как salted scrypt: N=131072, r=8, p=1. Одновременно допускаются две операции хеширования.
- Сессия — случайный 256-битный токен в HttpOnly cookie; в базе хранится SHA-256 токена. Срок — 30 дней; выход отзывает текущую сессию. Для пользователя сохраняется не более десяти сессий.
- Production cookie использует `Secure`, `SameSite=Lax` и префикс `__Host-`. Для локального HTTP `Secure` выключен. Пароли и сессионные токены не записываются в localStorage.
- После регистрации выдаётся случайный код восстановления, видимый один раз. Его следует сохранить в менеджере паролей. Восстановление меняет пароль, отзывает все старые сессии и выдаёт новый код. Сервер хранит только хеш кода. Без пароля и кода самостоятельное восстановление в этой версии невозможно.
- В базе находятся логин, хеши, сроки сессий, пройденные уроки и черновики. Пользовательский код API не исполняет.

Запросы изменения проверяют точный `Origin` и заголовок `X-Lumo-Request: 1`. Для данных аккаунта дополнительно требуется его ID в `X-Lumo-Account`: это предотвращает запись черновика старой вкладки в аккаунт, открытый в другой вкладке. SQL-запросы параметризованы; сервер проверяет поля прогресса, номера уроков и длину черновиков.

Вход, регистрация и восстановление имеют общий предел 20 запросов за 15 минут с одного IP. Для API установлен предел 180 запросов в минуту. Учебные задания не имеют таймера. Счётчики запросов находятся в памяти одного процесса; при нескольких экземплярах сервера нужен общий store ограничения запросов.

## Как объединяются изменения

1. Без входа используется прежний ключ `lumo.learning.v1`. Вход и выход сохраняют этот гостевой прогресс отдельно.
2. У каждого аккаунта своя локальная копия `lumo.account.<id>`: текущий прогресс, последняя согласованная копия и версия. Она остаётся в браузере после выхода, чтобы не терять ещё не отправленные правки. На общем компьютере учитывайте это при выборе места работы.
3. Гостевой прогресс добавляется к аккаунту только по выбранному флажку. Уже пройденные уроки объединяются.
4. Изменения черновиков и прохождения отправляются через секунду после последнего изменения. При возврате во вкладку, восстановлении соединения и раз в 30 секунд выполняется обновление. Есть ручная кнопка синхронизации.
5. Сервер принимает запись только для актуальной версии. При несовпадении отвечает 409 и возвращает новую копию. Клиент сравнивает локальную, серверную и последнюю общую версии.
6. Независимые черновики объединяются автоматически. Если один черновик изменился с обеих сторон, показываются обе версии. При добавлении гостевого варианта он показывается отдельно. Запись откладывается до выбора пользователя; после выбора снова проверяется серверная версия.
7. Правки, сделанные во время отправки запроса, остаются в редакторе и отправляются следующим запросом. Фоновая синхронизация не переключает текущий урок. Новое устройство начинает с последней отправленной копии; навигация сохраняется локально при каждом действии и попадает на сервер вместе с изменениями ответов или прохождения.
8. При недоступной сети открытый аккаунт продолжает сохранять правки локально. Если полностью перезагрузить сайт без доступного API, открывается гостевой режим; локальная копия аккаунта сохраняется и будет восстановлена после входа. Для полной загрузки самого сайта без сети service worker пока не добавлен.

Факт прохождения остаётся достижением, даже если позже изменить ответ. Проверки заданий выполняются в браузере; сохранённый прогресс не является защищённой экзаменационной оценкой.

## API

| Метод и путь | Назначение |
| --- | --- |
| GET `/api/health` | Проверка работающего процесса |
| GET `/api/ready` | Проверка процесса и подключения к базе, 200 либо 503 |
| POST `/api/auth/register` | `{username, password}` → аккаунт, сессия, копия прогресса и код восстановления |
| POST `/api/auth/login` | `{username, password}` → аккаунт, сессия и копия прогресса |
| POST `/api/auth/recover` | `{username, password, recoveryCode}` → новый пароль, сессия и новый код |
| GET `/api/session` | Текущий аккаунт с прогрессом или `{user:null}` |
| POST `/api/auth/logout` | Отзыв текущей сессии |
| GET `/api/progress` | `{revision, progress, updatedAt}` текущего аккаунта |
| PUT `/api/progress` | `{revision, progress}` → новая версия либо 409 с актуальной копией |

Ошибки — JSON с полем `error`; интерфейс переводит коды на RU/EN. Ответы API имеют `Cache-Control: no-store`. Журналы не содержат тела запросов, cookies, пароли или строки подключения.

## Внешний PostgreSQL и публикация

Для внешнего PostgreSQL задаётся `DATABASE_URL`. Пример формата — в `.env.example`; используйте проверяемый TLS и настройки поставщика базы. Таблицы из `schema.sql` создаются при запуске. Настройка не переносит содержимое локальной PGlite-базы автоматически.

Для production нужны `NODE_ENV=production`, HTTPS-адреса в `APP_ORIGINS` и `DATABASE_URL`. На Render точный адрес может поступить из `RENDER_EXTERNAL_URL`, если `APP_ORIGINS` не задан. Число доверенных reverse proxy задаётся явно в `TRUST_PROXY_HOPS`; не увеличивайте его без учёта схемы хостинга. `PORT` задаётся платформой, production по умолчанию слушает `0.0.0.0`. `pnpm build`, затем `pnpm start` запускает сервер, который обслуживает и `dist/`, и API. При отсутствии сборки production-запуск прекращается до подключения к базе.

Для публикации предпочтителен единый HTTPS-адрес сайта и API. GitHub хранит исходники; GitHub Pages самостоятельно не запускает Node.js API. Если фронтенд размещается отдельно, `VITE_API_URL` задаёт адрес API при сборке. Cookie должна работать в same-site контексте, например на собственных поддоменах. Случайная пара независимых доменов GitHub Pages и API с текущим `SameSite=Lax` не подходит для входа.

Локально проверена PGlite с настоящим PostgreSQL SQL-движком. Для драйвера `pg` добавлен отдельный тест PostgreSQL и сервис PostgreSQL 18 в GitHub Actions. Если `TEST_DATABASE_URL` не задан, этот тест пропускается. Его фактический запуск, внешнее подключение Neon и публичный HTTPS нужно подтвердить результатами соответствующего запуска. Ручные проверки скринридерами остаются открытыми.

## Проверки

```powershell
pnpm test:api
pnpm build
$env:PLAYWRIGHT_CHANNEL = 'chrome'
pnpm test:a11y
```

API-тесты проверяют регистрацию, вход/выход, хеши, защиту от запросов с чужого origin, изоляцию аккаунтов, конкурирующие записи, восстановление, отзыв сессий, ограничения запросов и сохранение базы после закрытия. Браузерные тесты используют отдельную базу в памяти на порту 3002 и не создают аккаунтов в `.data/lumo/`.

Они проходят работу двух независимых сессий, конфликт после потери связи, ввод во время сохранения, гостевой режим, восстановление доступа, RU/EN, фокус клавиатуры, axe и ширину 320 px с текстом 150%.

Первичные источники: [PGlite](https://pglite.dev/docs/), [node-postgres](https://node-postgres.com/features/connecting), [Node.js scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback), [OWASP: хранение паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP: защита от CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
