# Публикация Lumo: этап 8

Схема: GitHub хранит исходники и запускает проверки; Render обслуживает сайт и Express API по одному HTTPS-адресу; Neon хранит PostgreSQL. Это сохраняет вход через HttpOnly cookie и синхронизацию между устройствами.

**Состояние:** конфигурация подготовлена. Внешние Render/Neon ещё не подключены; публичный адрес сайта пока не получен. Адрес `127.0.0.1` открывается только на том устройстве, на котором запущен сервер.

Репозиторий: [ShiroHatS/Diplom-](https://github.com/ShiroHatS/Diplom-). Публикуются исходники, lock-файл, тесты и лицензии. `.env`, `.data/`, `node_modules/`, `dist/`, cookies и тестовые снимки в Git не входят. Учётные записи из локальной базы автоматически на сервер не переносятся. Гостевой прогресс браузера также относится к адресу сайта: у нового HTTPS-адреса будет отдельное локальное хранилище.

## 1. PostgreSQL в Neon

1. Подключить Neon в приложении или открыть [Neon Console](https://console.neon.tech/).
2. Создать отдельный проект `lumo` в плане **Free**. Выбрать регион рядом с Render. Сохранить имя проекта и базы.
3. В Connect выбрать обычную PostgreSQL-строку подключения. Для первого размещения использовать прямое соединение (без `-pooler`): приложение уже содержит пул максимум из пяти соединений.
4. Строка должна использовать проверяемый TLS, например параметр `sslmode=verify-full`. Не отключать проверку сертификата и не добавлять `rejectUnauthorized: false`.
5. Передать строку как секрет `DATABASE_URL` в Render. В GitHub-файлы и клиентские `VITE_*`-переменные её не записывать.

Таблицы создаются при запуске сервера из `server/schema.sql`. Это идемпотентная первоначальная схема; будущие изменения структуры потребуют версионируемых миграций. У бесплатного Neon есть ограничения объёма, вычислений и трафика; их актуальные значения указаны в [планах Neon](https://neon.com/docs/introduction/plans). Платный план не требуется для этой конфигурации.

## 2. Сайт и API в Render

После успешной загрузки исходников и проверок:

1. Подключить Render в приложении или открыть [Render Dashboard](https://dashboard.render.com/).
2. Выбрать New → Blueprint и репозиторий `ShiroHatS/Diplom-` с файлом `render.yaml`.
3. Сохранить **Free** для единственного сервиса `lumo-learning`. Файл не создаёт платных услуг или отдельной базы Render.
4. Ввести секрет `DATABASE_URL`, полученный в Neon. Проверить настройки перед запуском.
5. Дождаться статуса успешного размещения и сохранить фактический адрес вида `https://ИМЯ.onrender.com`. Имя назначает Render; этот пример не является работающей ссылкой.

Render автоматически задаёт `PORT` и `RENDER_EXTERNAL_URL`. Приложение использует этот точный HTTPS-адрес как разрешённый Origin. Значение `APP_ORIGINS` из локального `.env` переносить не нужно. При подключении собственного домена задать `APP_ORIGINS` со всеми точными разрешёнными HTTPS-адресами через запятую.

| Настройка | Значение |
| --- | --- |
| Node | `.node-version` |
| Build | `npm install --global pnpm@11.25.0 && pnpm install --frozen-lockfile --prod=false && pnpm build` |
| Start | `node server/index.js` |
| Health Check | `/api/ready` |
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `TRUST_PROXY_HOPS` | `1`, для стандартного reverse proxy Render; при другой схеме проверить заново |
| `DATABASE_URL` | секрет подключения Neon |
| Auto Deploy | After CI Checks Pass |

API не должен работать с PGlite в эфемерном файловом хранилище Render: данные там теряются после перезапуска. Production-запуск откажется работать без `DATABASE_URL`. Бесплатная база Render в шаблоне не используется, потому что она истекает через 30 дней. Эти ограничения описаны в [документации Render](https://render.com/docs/free).

Бесплатный Render подходит для демонстрации диплома: после 15 минут без запросов сервис засыпает, следующий запуск может занять около минуты. Не использовать периодические запросы только для обхода засыпания. Платёжные данные для этой конфигурации добавлять не нужно; перед любым изменением плана следует отдельно проверить стоимость и лимиты.

## 3. Автоматические проверки

`.github/workflows/ci.yml` запускается при push и pull request:

1. Устанавливает фиксированные Node/pnpm и зависимости из lock-файла.
2. Проверяет API, объединение прогресса, настройки размещения, HTTP-заголовки и работу обычного драйвера `pg` с отдельным PostgreSQL 18.
3. Собирает фронтенд и запускает браузерные тесты через Express, который отдаёт `dist` и API вместе. Поэтому проверяются также заголовки публичных файлов Python и изолированный запуск кода.

База GitHub Actions временная и не содержит пользователей сайта. Тест PostgreSQL создаёт отдельную схему со случайным именем и удаляет только её. Локально, если `TEST_DATABASE_URL` не задан, этот один тест пропускается. CI на внешнем сервере считается проверенным только после фактического успешного запуска; наличие YAML-файла не подтверждает успех.

Для локальной проверки уже установленных зависимостей:

```powershell
pnpm test:api
pnpm build
$env:PLAYWRIGHT_CHANNEL = 'chrome'
$env:LUMO_TEST_SERVE_SITE = '1'
pnpm test:a11y
Remove-Item Env:LUMO_TEST_SERVE_SITE
```

В обычном `pnpm test:a11y` по-прежнему доступен путь через Vite preview. В обоих вариантах используются отдельные тестовые аккаунты и база; сервер разработки на порту 5173 и его данные не затрагиваются.

## 4. Проверка опубликованного адреса

1. Открыть реальный HTTPS-адрес на компьютере и телефоне через мобильную сеть. Компьютер с локальным Vite можно выключить: внешний сайт должен продолжать работать.
2. Проверить `/api/ready`: ожидается `{"ok":true}`. При недоступной базе сервер возвращает 503 с `{"ok":false}`, без строки подключения.
3. В отдельном тестовом аккаунте сохранить код восстановления, пройти урок и войти со второго устройства. Проверить синхронизацию и отдельный гостевой режим после выхода.
4. Запустить `print("Привет")`, `console.log("Hello")` и HTML-предпросмотр. При ошибке загрузки Python проверить заголовки файлов `/runtime/python/`: CORS `*` разрешён только для публичных файлов среды, API остаётся с точным списком Origin.
5. В DevTools проверить cookie `__Host-lumo_session`: `HttpOnly`, `Secure`, `SameSite=Lax`, без `Domain`. На телефоне достаточно проверить вход/выход и повторное открытие.
6. Пройти настройки и аккаунт клавишами Tab/Shift+Tab/Escape. Повторить открытые проверки из [отчёта доступности](accessibility-audit.md), включая реальные скринридеры.

## 5. Обновление и восстановление

Изменения проходят проверки в GitHub; Render с `checksPass` разворачивает только прошедшие их изменения. Первая публикация может быть запущена вручную после зелёного CI. `/api/health` проверяет сам процесс, `/api/ready` дополнительно делает запрос к PostgreSQL.

HTML перепроверяется при открытии, а файлы с хешами в `assets/` кэшируются надолго. Файлы интерпретатора и остальные публичные ресурсы перепроверяются, чтобы не закреплять старую версию на год.

Перед изменениями схемы делать отдельную резервную копию PostgreSQL стандартным `pg_dump` и хранить её вне публичного Git. Копия содержит данные аккаунтов и черновики. Восстановление выполнять в отдельную тестовую базу и проверять до переключения. Откат кода в Render не откатывает базу.

Для восстановления ошибочного обновления выбрать предыдущий успешный deploy в Render. При изменениях схемы сначала проверить совместимость старого кода. Восстановление аккаунта пользователя выполняется личным кодом; оператору не нужно запрашивать пароль.
